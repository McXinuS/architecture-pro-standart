### <a name="_b7urdng99y53"></a>**Название задачи:** ADR-2. Передача ставок в кол-центр и партнёрский кол-центр
### <a name="_hjk0fkfyohdk"></a>**Автор:** Андрей Шаповалов
### <a name="_uanumrh8zrui"></a>**Дата:** 21.10.2026

Решение дополняет MVP открытия депозитов из [ADR-1](../Task3/README.md). Ставки по-прежнему ведутся и утверждаются в АБС, а Сервис депозитов хранит их копию.

### <a name="_qmphm5d6rvi3"></a>**Решение**

Диаграмма контекста: [c4-context.drawio](c4-context.drawio)

Диаграмма компонентов: [c4-component.drawio](c4-component.drawio)

**АБС**

- Процесс работы со ставками не меняется: менеджер бэк-офиса депозитов раз в день утверждает ставки в АБС. АБС остаётся единственным источником ставок (+R8).
- **Интеграционный сервис АБС** уже публикует ставки в Kafka (ADR-1). В нём появляется компонент **Выгрузка файла ставок**: при каждом утверждении он формирует CSV-файл с базовыми ставками и кладёт его на SFTP-сервер. Новых запросов к БД АБС нет, компонент использует те же ставки, что уходят в Kafka (+R4).
- Файл называется по дате и времени, например `deposit_rates_20270115_0930.csv`. Сначала файл записывается под временным именем и переименовывается после записи, чтобы партнёр не прочитал его частично. Старые файлы хранятся 30 дней.

**SFTP-сервер**

- Новый сервер в DMZ банка. Интеграционный сервис АБС записывает на него файлы из внутренней сети, партнёр подключается снаружи по ключу и может только читать свой каталог (+R12, +R13).
- В файле только базовые ставки, они и так опубликованы на сайте. Данных клиентов и персональных ставок в нём нет (+R13).

**Интернет-банк**

- **API ставок** Сервиса депозитов уже отдаёт ставки сайту и интернет-банку. Доработка — доступ для системы кол-центра. Сервис депозитов работает в двух ЦОД и масштабируется горизонтально, поэтому выдерживает рост звонков (R1, P2, P5). Запросов в АБС при этом нет (+R3).

**Система кол-центра**

- **Сервис ставок** — новый компонент на Java, Spring Boot. Он запрашивает ставки у Сервиса депозитов по REST/HTTPS. Ставки меняются раз в день, поэтому ответ можно кешировать на несколько минут.
- **Экран ставок** — новый экран на React.js, оператор открывает его во время звонка. Платформа кол-центра допускает расширение силами банка или подрядчика (+R1).

**Система партнёрского кол-центра**

- Партнёр сам дорабатывает свою систему: каждые 15 минут забирает новый файл с SFTP-сервера и показывает ставки операторам. Так ставки у партнёра обновляются не позже чем через 15 минут (R4).

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

1. **Система кол-центра читает ставки из Kafka и хранит копию у себя.** Отклонено для MVP: подрядчику пришлось бы делать свою базу ставок и обработку событий. Запрос к API Сервиса депозитов проще. Вариант можно рассмотреть, если нагрузка сильно вырастет.
2. **Система кол-центра получает ставки напрямую из АБС.** Отклонено: появится дополнительная нагрузка на АБС и второй путь получения ставок (+R3, +R4, +R8).
3. **Файл ставок формирует Сервис депозитов.** Отклонено: Сервис депозитов работает с данными клиентов интернет-банка, его связь с внешним SFTP-сервером увеличивает риски безопасности. Интеграционный сервис АБС получает ставки первым, сразу после утверждения.
4. **Менеджер бэк-офиса отправляет партнёру ставки по почте Excel-файлом.** Отклонено: это ручная работа каждый день, возможны ошибки и задержки. Подходит как запасной вариант, пока партнёр не доработал свою систему.
5. **Операторы партнёра смотрят ставки на сайте банка.** Отклонено: партнёр работает в своей системе и готов принимать именно файлы. Подходит как временный вариант при сбоях обмена файлами.

**Недостатки, ограничения, риски**

- Операторы кол-центров видят только базовые ставки. Персональные и специальные ставки по-прежнему согласует бэк-офис по заявке.
- Партнёр не может оформить заявку на депозит, он только консультирует и направляет клиента на сайт, в интернет-банк или в отделение.
- Если Сервис депозитов недоступен, операторы кол-центра банка не видят ставки. Риск снижает работа сервиса в двух ЦОД и кеш в системе кол-центра.
- SFTP-сервер — новый элемент инфраструктуры. Нужны администрирование, управление ключами партнёра и мониторинг: файл не сформирован или партнёр его не забрал.
- Сроки доработки системы партнёра банк не контролирует. До её готовности можно использовать отправку файла по почте.
- Перевод звонков в партнёрский кол-центр при перегрузке настраивается в телефонии и в этом решении не рассматривается.
- Выгрузку файла делает команда АБС, у которой и так много задач в MVP.

## RoadMap

RoadMap: [roadmap.drawio](roadmap.drawio)

- MVP делается в первом полугодии 2027 года, целевое решение — во втором.
- Сначала разворачиваются Kafka и основа АБС (T10, T1), затем Интеграционный сервис и Сервис депозитов (T6, T12). Каналы — сайт, интернет-банк и кол-центр — подключаются после готовности API ставок и заявок.
- SFTP-сервер и формат файла согласуются с партнёром заранее (T11), чтобы партнёр начал свою доработку (T21) параллельно с выгрузкой файла (T8).
- Ставки в обоих кол-центрах (T18, T21) должны появиться до конца MVP, то есть до запуска маркетинговой кампании.
- В целевом решении депозиты открываются автоматически, без бэк-офиса (T4, T5, T9), появляются накопительные счета (T15) и заявки по звонку в кол-центр (T20).
